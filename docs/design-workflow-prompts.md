# 디자인 작업 플로우 프롬프트

> SPOTCHU가 45개 화면(모바일 43 + 어드민 2)을 만들어낸 실제 순서를 재구성하고, 다른 프로젝트에 적용할 수 있는 프롬프트로 정리한 것.
> 커밋 이력(`ca9dcf4` → `31f9a18`)·`design.md`·핸드오프 `README.md`·`MEMORY.md`에서 도출했다.
>
> 각 프롬프트는 자기완결적이라 새 세션에 그대로 붙여넣어도 된다.

## SPOTCHU의 실제 순서

| 단계 | 커밋 | 한 일 |
|---|---|---|
| 0 | `ca9dcf4` | PRD·기능 문서 세팅 — **디자인 전에 무엇을 만들지 확정** |
| 1 | `94fb112` | 스캐폴드 + 디자인 핸드오프 정본화 |
| 2 | (Phase 0) | 토큰 이식: `colors_and_type.css` → `globals.css` → Tailwind |
| 3 | `9a2fd58`~`31f9a18` | **섹션 A~K를 목업 데이터로 구현** (섹션 1개 = 커밋 1개) |
| 4 | `6c698e1`~ | DB·Auth·실데이터 배선 |
| 5 | `893c52d`,`882b12e` | 테마 조정(화이트 전환·코랄 톤다운) |

**핵심 세 가지**

1. **화면이 먼저, 데이터는 나중.** 45개 화면을 목업으로 전부 만든 뒤에야 백엔드를 붙였다.
2. **섹션 = PRD 기능 = 커밋 1개.** A~K 각 섹션이 `docs/features/<메뉴>`와 1:1로 대응한다.
3. **톤 조정은 마지막.** 전체 화면이 있어야 색이 과한지 판단할 수 있다. 코랄 톤다운은 전 화면 완성 후에 나왔다.

## 01. 디자인 정본 편입

**언제**: 디자인 산출물(피그마 export, HTML 프로토타입, 스크린샷 세트)을 받은 직후.

```
디자인 산출물을 저장소에 편입하고 정본으로 선언해줘.

1. 받은 디자인 파일을 저장소 안 한 폴더에 넣고, 그 폴더에 README.md를 만들어줘.
   README에 반드시 포함할 것:
   - 이 산출물이 프로덕션 코드인지 레퍼런스인지 명시.
     프로토타입(CDN React, Babel-in-browser 등)이면 "재현 대상이지 복붙 대상이 아니다"를
     분명히 써줘
   - 그 안에서 무엇이 프로덕션 그대로 이식 가능한지 구분 (보통 SVG 에셋과 토큰 CSS)
   - 기준 캔버스 크기 (예: 390x844)
   - 화면 목록과 각각이 어느 기능 문서에 대응하는지

2. 저장소 루트에 design.md를 만들어줘. 여기엔 디자인 원칙·토큰 요약·화면 세트 표·
   공유 컴포넌트 매핑·접근성 기준·구현 순서만 담아.
   **토큰 값을 여기에 중복 정의하지 마.** 원천 파일을 가리키기만 해.
   중복하면 반드시 갈라진다.

3. 화면 세트를 표로 만들어줘: 섹션 | 화면 | 대응 기능 문서.
   섹션은 기능 문서와 1:1이 되게 잘라.
```

> **왜 "재현 대상"임을 명시하나**: 프로토타입을 그대로 가져다 쓰려는 시도가 반드시 나온다. SPOTCHU 핸드오프는 첫 페이지에 *"Babel-in-browser와 CDN React는 프로토타이핑 편의지 배포 전략이 아니다"*라고 못 박고, 대신 SVG 에셋과 토큰 CSS는 이식 가능하다고 구분해뒀다.

## 02. 토큰 이식 + 동기화 장치

**언제**: 화면을 하나라도 만들기 전에.

```
디자인 토큰을 코드로 이식해줘.

1. 원천 토큰 파일(colors_and_type.css 같은)을 읽고, 프로젝트의 전역 스타일
   :root 블록으로 옮겨줘. 값은 그대로. 주석에 원천 파일 경로를 적어줘.

2. 그중 자주 쓸 역할 색·폰트만 Tailwind(또는 쓰는 스타일 시스템)의 유틸로 노출해줘.
   전부 노출하지 마 — 자주 안 쓰는 건 var(--토큰)로 직접 참조하는 게 낫다.

3. **동기화 테스트를 하나 만들어줘.** 원천 파일과 코드의 :root에서 --* 값을 각각
   파싱해서 대조하고, 다르면 실패하는 테스트야.
   의도적으로 다르게 둔 토큰이 있으면 예외 목록에 이유와 함께 명시하게 해줘.

4. 만든 테스트를 지금 한 번 실행해서 통과하는지 보여줘.
```

> **3번이 이 단계의 핵심이다.** SPOTCHU는 `design.md`에 *"값은 원천 파일이 원천, 여기서 중복 정의 금지"*라는 좋은 규칙을 세웠는데도 실제로는 갈라졌다 — coral은 톤다운(`#FF5F6D`→`#e86b76`)됐고 cream은 화이트로 바뀌었는데, 둘 다 **원천 파일에는 반영되지 않았다.** 두 변경 다 의도적이고 근거도 남아 있었지만(커밋 메시지·인라인 주석), 원천으로 역류하지 않아 문서가 조용히 거짓이 됐다. 규칙만으로는 동기화가 안 된다.

## 03. 구현 순서 정하기

**언제**: 토큰 이식 후, 첫 화면을 만들기 전.

```
화면 구현 순서를 정해줘. 그냥 1번 화면부터 하지 마.

각 섹션에 대해 다음을 확인하고 표로 만들어줘:
- 외부 의존이 있는가 (지도 SDK, 결제, 푸시 등 API 키나 외부 계정이 필요한 것)
- 실제 데이터가 있어야 의미가 있는가, 목업으로 충분한가
- 다른 섹션이 먼저 있어야 하는가

그다음 순서를 제안해줘. 원칙:
- 가장 단순한 섹션(스플래시·온보딩 같은)을 맨 앞에 둬서 파이프라인 점검용으로 쓴다
- 재사용 프리미티브(버튼·칩·카드·뱃지)를 두 번째 섹션쯤에서 뽑아낸다
- **외부 키가 필요한 화면은 뒤로 미룬다.** 키 발급을 기다리느라 전체가 멈추면 안 된다
- 제품의 핵심 화면은 가능한 앞으로 (거기서 디자인 판단이 가장 많이 나온다)

디자인 산출물에 권장 순서가 있으면 참고하되, 위 기준과 충돌하면 조정하고
왜 바꿨는지 적어줘.
```

> **실제로 순서를 바꿨다.** SPOTCHU 핸드오프는 A→B→C→D를 권장했지만 실제 구현은 A→B→**D→C**였다. C(탐색·지도)가 Google Maps 키를 필요로 했기 때문이고, 그 판단이 `MEMORY.md`에 *"Google Maps(C1 키 필요)"*로 기록돼 있다. 권장 순서를 그대로 따랐다면 키를 기다리며 멈췄을 것이다.

## 04. 섹션 단위 화면 구현 (반복)

**언제**: 섹션마다 한 번씩. 한 섹션 = 한 세션 = 한 커밋.

```
섹션 <X>(<화면 목록>)를 구현해줘.

시작 전에:
1. 이 섹션에 대응하는 기능 문서(spec/rules)를 먼저 읽고, 인수 조건을 확인해줘
2. 디자인 산출물에서 이 섹션의 화면 소스와 카피·치수를 확인해줘.
   임의로 문구나 간격을 만들지 마 — 산출물에 있는 값을 쓴다

구현:
3. 목업 데이터로 만들어줘. 이 단계에서 DB나 API를 붙이지 마
4. 이미 만든 공유 컴포넌트가 있으면 재사용하고, 이 섹션에서 새로 필요한
   프리미티브가 생기면 공유 위치로 빼줘
5. 토큰을 쓰고 하드코딩 색을 넣지 마

끝나고:
6. 브라우저로 실제 렌더를 확인하고 콘솔 에러가 0인지 봐줘
7. 무엇을 만들었고 무엇이 남았는지 MEMORY.md에 한 줄로 기록해줘 —
   다음 세션이 이어받을 수 있게, 남은 섹션 목록도 같이
```

> **7번이 세션 경계를 만든다.** SPOTCHU는 섹션 커밋 사이사이에 `docs(memory)` 커밋이 있고(`1413c3f`, `77bfcb7`, `70a3c47`), 거기에 *"남음: C·E·F·G·H·I·J·K"* 식으로 잔여 목록이 적혀 있다. 45개 화면을 여러 세션에 걸쳐 만들 때 이게 없으면 매번 현황 파악부터 다시 한다.

## 05. 목업 → 실데이터 전환

**언제**: 화면이 전부(또는 대부분) 만들어진 뒤.

```
목업 데이터를 실제 데이터로 전환해줘.

1. 먼저 목업이 어디에 있고 어떤 모양인지 정리해줘. 화면들이 목업의 어떤 필드를
   기대하는지 목록으로 만들어줘 — 이게 사실상 스키마 요구사항이다

2. 그 요구사항과 기존 스키마 문서를 대조해서 차이를 보여줘

3. 목업과 실데이터를 같은 인터페이스 뒤에 두고 환경변수로 전환하게 만들어줘.
   화면 코드는 어느 쪽인지 몰라야 한다

4. 한 번에 다 바꾸지 말고 화면 단위로 전환하면서, 각 단계마다 실제로 렌더되는지
   확인해줘
```

> 화면을 먼저 만들면 **목업이 스키마 초안 역할**을 한다. SPOTCHU는 `lib/mock.ts`로 45개 화면을 채운 뒤 그 모양을 기준으로 Prisma 스키마와 서버 액션을 붙였고, `DATA_SOURCE` 환경변수로 목업/DB를 전환하는 façade를 뒀다.

## 06. 톤 조정 — 맨 마지막

**언제**: 전체 화면이 다 있고, 실제로 써본 뒤.

```
전체 화면을 훑고 톤을 조정해줘.

1. 주요 화면들을 실제로 렌더해서 보고, 과하거나 부족한 지점을 짚어줘.
   개별 화면이 아니라 **연속으로 봤을 때** 어떤지를 봐줘
2. 조정이 필요하면 토큰 수준에서 바꿔줘. 개별 컴포넌트에서 색을 덮어쓰지 마
3. 토큰을 바꿨으면 **원천 파일과 design.md도 같이 갱신해줘.**
   코드만 바꾸면 원천이 거짓이 된다
4. 커밋 메시지에 무엇을 왜 바꿨는지 값까지 적어줘
   (예: "style(theme): 코랄 톤다운 #ff5f6d→#e86b76")
```

> **왜 마지막인가**: 화면 3개만 보고는 코랄이 과한지 알 수 없다. SPOTCHU의 톤 조정 두 건(`893c52d` 화이트 전환, `882b12e` 코랄 톤다운)은 모두 섹션 A~K가 전부 끝난 뒤에 나왔다.
>
> **3번을 빠뜨리면** 02단계에서 만든 동기화 테스트가 바로 실패한다 — 그게 그 테스트의 존재 이유다.
