# 새 프로젝트 하네스 세팅 프롬프트

> 다른 저장소에 Claude Code 하네스를 세팅할 때 순서대로 붙여넣는 프롬프트 모음.
> 각 프롬프트는 **자기완결적**이라 새 세션에서 그대로 써도 된다.
> SPOTCHU 구조를 복사하는 게 아니라, 대상 저장소를 **먼저 조사하게** 만드는 것이 핵심이다.
>
> 출처: SPOTCHU 하네스 운영 경험(2026-09-03). 각 단계의 "왜"는 실제 실패 사례에서 나왔다.

## 어디서 멈춰도 되나

| 여기까지 | 얻는 것 |
|---|---|
| 01–02 | 실제로 작동하는 최소 하네스. **대부분의 프로젝트는 여기서 충분하다** |
| 03–04 | 여러 세션·여러 작업자가 같은 기준으로 일함 |
| 05–06 | 규칙이 사람 기억이 아니라 도구로 강제됨 |

**만들지 말 것**: 빈 `skills/` 디렉터리, 쓰지 않을 에이전트 여러 개, 강제되지 않는 규칙을 CLAUDE.md에 쌓는 것. 층은 필요해질 때 하나씩 켠다.

## 01. CLAUDE.md — 안내판 만들기

**언제**: 저장소를 만든 직후. 가장 먼저.

```
이 저장소를 파악해서 CLAUDE.md를 만들어줘.

먼저 조사부터 해줘. 의존성 매니페스트(package.json·pyproject.toml·go.mod 등 — 무엇이든,
없으면 없다고 해)·README·디렉터리 구조를 읽고, 커밋이 있으면 최근 30개까지 읽어서
이 프로젝트의 스택, 도메인, 현재 단계(프로토타입인지 운영 중인지)를 파악해.
추측하지 말고 파일 근거를 들어서 말해줘. 모르는 건 모른다고 해.

그다음 CLAUDE.md를 작성해. 짧게 유지해 — 다음만 담아:

- 프로젝트 한 줄 설명과 대상 사용자
- **기준 날짜** — 문서 첫머리에 박아줘. "현재 단계" 같은 서술은 날짜가 없으면
  갱신이 밀렸을 때 조용히 거짓이 된다. 갱신 책임 문장도 같이 넣어:
  "이 절은 시간이 지나면 거짓이 된다. 작업을 마칠 때 기준일과 함께 갱신한다"
- 문서 우선순위 (작업 전 읽어야 할 파일을 순서대로)
- **구현 전 문서 확인 절차** — 추상적으로 "문서를 읽어라"가 아니라 실행 가능한 형태로:
    grep -rn "<주제 키워드>" <원천문서> docs/
  그 주제에 대한 결정이 이미 있으면 그걸 먼저 제시하고 시작한다.
  사용자가 그 결정을 뒤집는 지시를 하면, 구현하기 전에
  "이건 문서 X절에 반대로 명시돼 있다"를 반드시 먼저 알린다
- 고정된 기술 스택 (임의 대체 금지 목록)
- 도메인 불변식 — **반드시 두 갈래로 나눠서 써줘.** 뭉뚱그리면 읽는 사람이
  무엇이 실제로 막히는지 모른다:
    · "코드가 강제하는 것" — 깨면 테스트/훅이 실패한다. file:line을 달아라
    · "문서에만 있는 것" — 사람이 지켜야 한다. 강제 장치가 없음을 밝혀라
  둘 다 grep 가능한 짧은 문장으로. 없으면 "현재 없음"이라고 명시해
- 매번 승인이 필요한 고위험 행동 (배포·DB 마이그레이션·git push·삭제).
  **항목마다 왜인지 한 구절씩 붙여줘.** 이유 없는 금지는 지켜지지 않는다
- 자주 쓰는 명령 — **실제로 실행되는 명령만. 무엇으로 실행하든 상관없다**
  (npm 스크립트든 python 파일이든 셸 한 줄이든). 없는 명령은 쓰지 마
- 정의된 완료(DoD) 4~5줄

규칙을 많이 쓰지 마. 강제되지 않는 규칙은 부채야. 여기 적는 건 "안내판"이고,
반드시 지켜야 하는 건 다음 단계에서 훅과 테스트로 옮길 거야.

마지막으로, **인용한 file:line을 전부 되짚어서 실제로 그 줄인지 확인한 뒤에**
완료라고 말해줘. 명령도 실제로 한 번씩 돌려봐. 확인 안 된 근거는 없느니만 못하다 —
틀린 줄 번호가 근거처럼 보이면 다음 사람이 그걸 믿는다.
```

> **왜 조사부터?** 스택을 잘못 적은 CLAUDE.md는 매 세션 잘못된 전제를 주입한다. 첫 파일이 가장 오래 남으므로 근거 없이 쓰지 않게 만든다.

## 02. settings.json — 게이트 켜기

**언제**: 1단계 직후. 여기까지가 하네스의 최소 단위.

```
.claude/settings.json을 만들어서 게이트를 켜줘.

1. 이 저장소에서 lint·typecheck·test에 해당하는 명령이 무엇인지 파악해줘.
   npm 스크립트일 수도 있고, python 파일이나 셸 한 줄일 수도 있다.
   해당하는 게 없으면 무엇을 추가해야 하는지 먼저 알려줘 —
   **없는 도구를 새로 들여오는 게 스택 원칙과 충돌하면 그것부터 말해줘.**

2. 검증 명령이 여러 개이고 러너가 서로 다르면(예: python 1개 + node 2개),
   **셋을 순차 실행하고 종료 코드를 합치는 러너 하나를 먼저 만들어줘**
   (verify.py 같은 것). 훅이 걸 대상이 하나여야 한다.
   훅은 임의 셸 명령을 부를 수 있으므로 package.json은 필요 없다.

3. .claude/settings.json 작성:
   - permissions.allow — 읽기 전용·검증 명령만 (lint, typecheck, test)
   - permissions.ask — 되돌리기 어려운 것만 (git push, rm, 배포, 마이그레이션).
     너무 많이 넣지 마. 승인 요청이 잦아지면 전부 습관적으로 통과시키게 돼서
     오히려 게이트가 무력해진다
   - hooks.PostToolUse (matcher: Edit|Write) — 포맷
   - hooks.Stop — 타입체크
   - 모든 훅 커맨드 끝에 2>&1 을 붙여줘. tsc 같은 도구는 에러를 stdout에 쓰는데
     훅이 stderr만 보고하면 실패가 조용히 묻힌다

4. 마지막이 제일 중요해. 훅 커맨드를 직접 실행해서 exit code와 출력을 보여줘.
   지금 실패한다면 — 의존성 미설치든 기존 타입 에러든 — 훅을 켜기 전에 그걸 먼저
   고치거나, 못 고치면 해당 파일을 검사 대상에서 빼줘.
   항상 실패하는 훅은 없느니만 못하다. 무시하는 습관이 생기고, 그때부터 진짜 실패도
   안 보이게 된다. 초록인 걸 확인한 다음에 완료라고 말해줘.
```

> **4번을 빼지 마라.** 이 세팅이 실패하는 가장 흔한 방식은 훅이 안 만들어지는 게 아니라, **만들었는데 처음부터 빨간 상태로 방치되는 것**이다. 그러면 몇 세션 안에 모두가 훅 출력을 스킵하게 된다.
>
> 실제 사례: SPOTCHU의 Stop 훅은 `@playwright/test` 미설치로 `exit=1`이 계속 났는데, `2>&1`이 없어 `No stderr output`이라는 성공처럼 보이는 메시지만 나왔다. 세션 전체가 게이트 없이 흘러갔다.

## 03. collaboration.md — 작업 흐름 고정

**언제**: 두 명 이상(사람이든 에이전트든)이 같은 저장소를 만지기 시작할 때.

```
docs/collaboration.md를 만들어줘. 어느 작업자가 받아도 같은 기준으로
협업하게 만드는 규칙 문서야. 다음 구조로:

1. 하네스 5층이 이 저장소에서 각각 무엇에 매핑되는지 표로
   (1 규칙/기억 · 2 스킬 · 3 훅/권한 · 4 에이전트 · 5 플러그인).
   아직 없는 층은 "없음(필요해지면 추가)"라고 솔직히 써.
   빈 디렉터리를 미리 만들지 마

2. 작업 흐름 — 한 작업 = 한 PR 기준으로 번호 매겨서:
   읽기 → 브랜치 → 구현 → 검증 → 리뷰 → PR → 기록

3. "구현 전 문서 확인"은 CLAUDE.md(01단계)에 이미 있다. 여기서는 그것을
   작업 흐름 몇 번째 단계인지 자리만 지정하고, 내용은 참조만 해줘. 중복 서술 금지

4. 정의된 완료(DoD) — CLAUDE.md 것을 참조만 하고 중복 서술하지 마

5. 충돌·미결정 처리: 미정 값은 발명하지 않는다. 해당 문서의 TODO에 남긴다

원칙 한 줄을 문서 상단에 박아줘:
"CLAUDE.md는 안내판이지 강제 장치가 아니다. 반드시 지켜야 하는 것은
3층(훅·권한)과 테스트로 옮긴다."
```

> **3번이 핵심이다.** 문서에 결정이 이미 있는데도 확인하지 않고 구현하는 건 가장 비싸고 흔한 실패다. 외부 조사로 얻은 결론이 *우연히 문서와 일치하면* 더 위험하다 — 검증했다는 감각만 남고 정작 문서를 안 읽게 된다.
>
> 실제 사례: 비교 앱 리서치로 "4탭 유지 + 제보는 FAB"를 권장했는데, PRD에 이미 같은 결정이 글자 그대로 있었고 `rules.md`엔 "탭 추가는 PRD 개정 없이는 금지"라는 불변식까지 있었다. 아무도 문서를 안 읽어서 그대로 위반하고 머지했고, 문서 8개 파일 16곳을 되돌리는 후속 PR이 필요했다.

## 04. /handoff — 세션 인수인계

**언제**: 한 작업이 여러 세션에 걸치기 시작할 때.

```
.claude/commands/handoff.md 를 만들어줘. 세션을 마무리하며 다음 작업자가
바로 이어받게 하는 커맨드야. frontmatter에 description 한 줄 넣고, 본문은
지시문으로. 다음을 수행하게 해줘:

1. 완료한 일 / 진행 중인 일 / 다음에 할 일 요약
2. 새로 내린 중요한 결정이 있으면 MEMORY.md에 추가 (무엇을·왜)
3. 두세 번 이상 실패한 접근이 있으면 ERRORS.md에 추가 (증상→시도→원인→해결)
4. 미결정/TODO가 생겼으면 해당 문서의 TODO 절에 반영
5. 현재 브랜치·변경 파일·남은 인수 조건 정리
6. git이 추적하지 않는 산출물(untracked)이 남아 있는지 확인하고 보고.
   워크트리를 쓰는 저장소면 다른 워크트리의 잔재도 확인해줘
7. 파괴적 작업(커밋·푸시·배포)은 사용자 승인 없이 하지 않는다

MEMORY.md와 ERRORS.md가 없으면 빈 파일을 헤더만 넣어서 같이 만들어줘.
```

> **6번은 실제 사고에서 나왔다.** 한 세션의 리서치 산출물이 커밋되지 않은 채 워크트리에만 남아 유실 직전까지 갔고, 다른 워크트리엔 같은 파일의 구버전이 방치돼 있었다.

## 05. code-reviewer — 자기 검토 분리

**언제**: 구현과 검토를 같은 패스에서 하는 게 불안해질 때. 에이전트는 이거 하나로 시작한다.

```
.claude/agents/code-reviewer.md 를 만들어줘.

frontmatter: name, description, tools는 Read/Grep/Glob만 (수정 권한 없음).
본문은 이 저장소 전용 체크리스트로 만들어줘 — 일반론 말고,
CLAUDE.md에 적힌 실제 불변식과 고위험 항목을 그대로 가져와서 항목화해.

반드시 포함할 것:
- 파일을 수정하지 않는다는 지시를 본문 첫 줄에 명시
- 요청 범위만 변경했는가 (무관한 리팩터가 섞이지 않았는가)
- 문서-코드 일치 — 이 변경이 문서에 적힌 결정과 어긋나지 않는가
- 차단 시 위반 항목과 근거를 파일:라인으로 제시
- 통과 시에도 남은 위험을 메모

만들고 나서, 지금 작업 중인 브랜치에 대해 한 번 실제로 돌려서
체크리스트가 쓸모 있는지 확인해줘.
```

> **만들었다고 쓰이지 않는다.** 에이전트를 아홉 개 갖춰두고도 한 번도 호출하지 않는 일이 실제로 벌어진다. 하나만 만들고, 만든 즉시 한 번 돌려서 실효를 확인하는 편이 낫다.

## 06. 불변식을 테스트로 (선택)

**언제**: 같은 규칙이 두 번 이상 깨졌을 때. **그 전엔 하지 마.**

```
CLAUDE.md와 각 rules 문서에 적힌 불변식 중에서, 코드로 검증 가능한 것을
골라서 테스트로 옮겨줘.

먼저 후보를 목록으로 보여주고 시작해. 각 후보에 대해:
- 문서의 어느 문장인지
- 코드의 어느 값과 대응하는지
- 자동 검증이 가능한지, 가능하면 어떻게

문서와 코드가 짝을 이루는 것부터 우선해줘. 예를 들어 "화면 하단 탭은 정확히 N개"
같은 규칙이면, 문서의 숫자와 실제 구현의 배열 길이를 대조하는 테스트를 만든다.

전부 자동화하려 하지 마. 깨졌을 때 가장 비싼 것 3~4개만 골라.
나머지는 문서에 남겨두는 게 낫다.
```

> 산문으로 쓴 금지 조항은 지켜지지 않는다. *"탭 추가는 문서 개정 없이는 금지"*라고 명시돼 있어도, 그 문장을 읽지 않으면 없는 것과 같다. 테스트는 읽지 않아도 막는다.
