> **v2 — Flow A 재작성.** 최초 버전은 "Instagram 스토리 링크 스티커 자동 첨부"를 전제했으나, Meta 공식 문서 실측 결과 그 기능이 공개 API에 없음을 확인(§기술 전제 참고). 자체 소유 딥링크 + OS 표준 공유 시트 방식으로 대체.

> **v5 — 주 타깃을 Instagram으로 확정, Flow B 단순화 + Flow A 보류.** (v6에서 전제가 뒤집히며 무효화됨 — 아래 v6 참고)
> **v10 — 공유 페이로드 미지수 규명 + 플랫폼 선택지 정리 + 비용/보안 보강 + Flow A 구현 현황 정정.** (1) **공유 시트 경로는 oEmbed와 다른 통로**임을 분리해 명시하고, "페이로드에 캡션이 오는가"를 **D-0(최우선 스파이크)**으로 신설 — 원래 요청의 성립 여부가 여기서 결정된다. (2) iOS 공유 수신을 위한 **플랫폼 선택지(PWA / Capacitor / Flutter / 네이티브 2벌)**를 비교 정리하고, Flutter 선택 시 **서버 액션 6개 → REST API 신규 구축**이 필요하다는 저장소 실측 결과를 포함(§D-9). (3) 비용: **Autocomplete를 세션 토큰으로 묶으면 무료**임을 확인해 저장 1건당 과금 ≈ 1회로 정정, 함정 2개(세션 토큰·필드 화이트리스트)를 구현 규칙으로 고정. (4) 보안: **Places는 서버 전용 키를 별도 발급**해야 함(현재 `NEXT_PUBLIC_` 키만 존재 — 노출 키에 Places를 켜면 과금 도용 위험). (5) `embed.js` 제3자 스크립트의 CSP·개인정보 고지 사안 신설(D-10). (6) **Flow A는 이미 구현돼 있음**(`ShareButton.tsx`) — 문서가 "미구현 제안"으로 서술해 온 것을 정정.
> **v9 — 실제 엔드포인트 호출로 Flow D 핵심 전제 붕괴·재설계.** 토큰리스 oEmbed를 실제로 호출(2026-09-08)한 결과, **응답에 캡션이 없다는 것이 확정**됐다 — 반환 필드는 `version`·`provider_name`·`provider_url`·`type`·`width`·`html` 6개뿐이고, `html`은 로딩 스켈레톤이라 가시 텍스트가 `"View this post on Instagram"` 한 줄이다. 캡션·해시태그는 사용자 브라우저에서 `embed.js`가 렌더링하며, 그 결과물은 교차 출처 iframe이라 클라이언트 JS로도 읽을 수 없다. **따라서 "#태그를 바탕으로 위치를 제안한다"는 최초 요청은 API로 구현 불가능**하고, Flow D는 "임베드 + 사용자가 직접 지정한 장소 + 지도 + 컬렉션 저장"으로 축소된다. 인터랙션 흐름·화면 상태를 그 기준으로 다시 썼고, §D-7을 결정 사항에서 제약으로 바꿨다(대안 D-7a/b/c 비교표 추가). 에러 응답 형태도 실측해 화면 상태에 반영. **문서 조사(1차 출처)로는 여기까지 못 왔다 — Meta 공식 샘플 응답이 `html` 값을 잘라놨기 때문에 실측이 필요했다.**
> **v8 — Flow D 기술 전제 1차 출처 재검증.** v7 초안이 2차 출처(기술 블로그·서드파티 API 요약)를 근거로 쓴 것이 확인되어 전 항목을 1차 출처로 교차 검증했다. 핵심 결론 두 가지(**심사 불필요**·**좌표 자동확정 불가**)는 Meta 공식 블로그·공식 문서로 **확증**됐으나, 세부 4건이 틀려 정정했다 — 공유시트 지원 범위(Android 전용 → Chromium 전반, Safari·Firefox 미지원), oEmbed 응답 필드(`author_name`·`thumbnail_url` 전제 삭제, `html`만 신뢰), 삭제 의무(24h 규정 없음 + 삭제 수단 제공 의무 신규), **Places/Geocoding 단가(결론 역전 — Text Search Essentials가 Geocoding보다 싸고 정확)**. 상세: §기술 전제 Flow D "정정 이력". 이 문서의 기술 전제는 앞으로 **1차 출처만** 근거로 쓴다.
> **v7 — Flow D 추가(신규 요청).** "Instagram에서 본 지역 피드를 해시태그와 함께 SPOTCHU로 넘겨 구글맵에 위치를 띄우고 내 컬렉션에 저장한다"는 요청을 문서화. Flow C와 방향은 같으나(Instagram → SPOTCHU) **대상이 남의 게시물이고 결과물이 `Post`가 아니라 개인 저장**이라 메커니즘이 전혀 다르다. (기술 전제는 v8에서 재검증·정정됨)
> **v6 — Flow B 폐기, Flow A로 통합.** "SPOTCHU가 Instagram Stories Sharing을 직접 실행해 배경 이미지를 프리필한다"는 Flow B의 핵심 메커니즘을 Meta 공식 문서로 재확인한 결과, 이 기능은 **네이티브 앱 전용**(iOS는 `UIPasteboard`, Android는 `content://` URI + Intent extras 필요)이라 **PWA인 SPOTCHU는 표준 웹 API로 구현 자체가 불가능**함을 확인(§기술 전제). PWA가 실제로 쓸 수 있는 건 Flow A와 동일한 Web Share API(`navigator.share()`)뿐이라, Flow B를 폐기하고 Flow A로 통합. Flow A는 다시 핵심 흐름(보류 해제)이 되고, 인터랙션 흐름·화면 상태를 Web Share API 기준으로, 딥링크 랜딩을 PWA 실제 동작 기준으로 다시 썼다. 워터마크는 여전히 제거 상태 유지(v5 판단 존속 — 무엇을 올리든 안 눌리는 장식이라는 결론은 채널 수와 무관), 텍스트 URL은 복원(카카오톡·문자·이메일에선 실제로 하이퍼링크됨 — v5의 "URL 무의미" 판단은 Instagram 단일 채널 전제에서만 유효했던 것으로 확인).

## 목적

SPOTCHU와 Instagram 사이의 콘텐츠 흐름을 정의한다. 방향이 서로 다른 두 흐름이다.
- **Flow A(내보내기+복귀)**: SPOTCHU 콘텐츠를 카카오톡·문자·이메일·Instagram·X 등 **사용자가 고른 아무 채널로나** 공유하고, 받는 사람이 링크를 탭하면 SPOTCHU로 돌아오게 한다(발견 채널 확장). SPOTCHU가 트리거. Web Share API(`navigator.share()`) 기반이라 모든 채널이 같은 하나의 메커니즘을 쓴다 — Instagram만 특별 취급하지 않는다(할 수도 없다 — 아래 폐기된 Flow B 참고).
- **Flow C(Instagram → SPOTCHU 역가져오기)**: Instagram에 올린 게시물을 SPOTCHU가 감지해서 가져오는 흐름. **Instagram이 트리거** — Flow A와 방향이 정반대이고 메커니즘도 완전히 다르다(공유 시트/딥링크가 아니라 Instagram Graph API 연동).
- **Flow D(남의 게시물 → 내 지도·컬렉션)**: 사용자가 Instagram에서 본 **남의** 지역 피드를 SPOTCHU로 넘기면, 그 게시물을 임베드로 띄워놓고 **사용자가 장소를 지정**해 구글맵에서 위치를 확정한 뒤 **자기 컬렉션에 저장**하는 흐름. **사용자가 트리거**(Flow C의 자동 폴링과 다름). 결과물이 공개 `Post`도 공개 `Spot`도 아닌 **개인 저장**이라는 점이 Flow C와의 결정적 차이다.
  > 최초 요청은 "#태그를 바탕으로 위치를 자동으로 보여준다"였으나, **실측 결과 캡션이 API 응답에 없어 자동 추정은 불가능**하다(§기술 전제 Flow D). 장소 지정은 사용자가 한다.

> **Flow C vs Flow D — 헷갈리기 쉬우니 고정한다**
>
> | | Flow C | Flow D |
> |---|---|---|
> | 대상 게시물 | **내** 게시물 | **남의** 게시물(공개) |
> | 트리거 | 서버 폴링(자동) | 사용자가 공유/붙여넣기(수동) |
> | 계정 연결 | 필요 — **프로 계정(비즈니스/크리에이터) 전용, 개인 계정은 API 자체가 안 열림** | **불필요**(공개 게시물이면 계정 종류 무관) |
> | Meta App Review | **필수**(2~4주, 승인 불확실) | **불필요**(2026-06 토큰리스) |
> | Business Verification | **필수** — 내가 소유·관리하지 않는 계정을 서비스하려면 Advanced Access가 필요하고, 그 조건에 사업자 인증이 포함된다 | **불필요** |
> | 결과물 | 공개 `Post`(스팟 연결 필수) | 내 컬렉션 저장(비공개) |
> | 저장 이미지 | SPOTCHU가 호스팅 | **호스팅 안 함**(permalink만) |

> **폐기된 Flow B**: "SPOTCHU가 Instagram Stories Sharing을 직접 실행해 배경 이미지를 프리필한다"는 안을 검토했으나, Meta 공식 문서 확인 결과 이 기능은 **네이티브 앱 전용**이라 PWA인 SPOTCHU는 표준 웹 API로 구현할 수 없다(§기술 전제). Flow A로 통합.

## ⚠️ 기술 전제 (실측 완료)

### Flow A — Instagram 전용 API에 의존하지 않는다
처음엔 "Instagram Stories Sharing으로 스토리에 링크 스티커를 자동으로 붙이면, 시청자가 스와이프해서 SPOTCHU로 돌아온다"는 안을 검토했으나 **실제로 안 된다**. Meta 공식 문서(`developers.facebook.com/docs/instagram-platform/sharing-to-stories/`)를 직접 확인한 결과:

- 문서에 정의된 파라미터는 배경 이미지·스티커 **이미지**·배경색뿐이다(iOS: `com.instagram.sharedSticker.backgroundImage`/`stickerImage`/`backgroundTopColor`/`backgroundBottomColor`, Android: `interactive_asset_uri` 등). **URL·링크·attribution 파라미터는 어디에도 없다.**
- 과거 Spotify·SoundCloud·GoPro가 스토리에 탭 가능한 링크를 붙일 수 있었던 건 공개 API가 아니라 **Meta와의 별도 파트너십 심사**를 통과했기 때문이다(2018 TechCrunch 보도). SPOTCHU가 같은 걸 하려면 Meta 파트너 신청이 필요하고 승인은 보장되지 않는다.
- Meta Ads(광고 CTA 딥링크)·Instagram Shopping(상품 태그)도 검토했으나 둘 다 무관: 광고는 **광고주가 돈을 내고 캠페인을 만들 때만** 쓰는 필드이고, 쇼핑은 **실물 상품 판매 사업자**만 자격이 된다(SPOTCHU는 둘 다 해당 없음).
- **(v6 추가) Stories Sharing 자체가 네이티브 앱 전용이다.** 링크 스티커가 아니라 "배경 이미지 프리필"만 쓰더라도, 이 기능을 호출하려면 iOS는 `UIPasteboard`에 Instagram 전용 키로 데이터를 써야 하고, Android는 로컬 파일을 가리키는 `content://` URI를 Intent extra로 넘겨야 한다 — Meta 문서 원문: *"이 문서는 네이티브 앱(iOS/Android)에만 적용됩니다... 표준 웹 API로는 구현할 수 없습니다."* PWA의 `navigator.clipboard`는 범용 MIME 타입(text/plain, image/png)만 쓰고 Instagram 전용 pasteboard 키를 못 쓰며, 웹페이지는애초에 `content://` URI를 만들 수 없다. **즉 SPOTCHU가 PWA인 이상, Instagram Stories 배경 이미지를 자동으로 프리필해서 여는 것 자체가 불가능하다.**

**결론**: Instagram 안에서 "게시물/스토리에 탭 가능한 SPOTCHU 링크가 자동으로 박히는" 것도, "배경 이미지가 자동으로 프리필된 상태로 스토리 작성화면이 열리는" 것도 PWA로는 불가능하다. 대신 다음 조합으로 간다 — 이건 인스타그램 승인이 전혀 필요 없고, 모든 채널에 동일하게 적용된다.

| 구성요소 | 정체 | 비용 | 승인 |
|---|---|---|---|
| Web Share API(`navigator.share()`) | 브라우저 표준 API — 호출하면 OS 공유 시트가 뜬다(iOS Safari·Android Chrome 지원, Firefox 등 일부 미지원) | 무료 | 불필요(웹 표준) |
| 자체 딥링크 도메인 | `spotchu.app/spot/{id}` — SPOTCHU가 소유한 일반 웹페이지 URL | 무료 | 불필요 |
| (안드로이드만) Digital Asset Links | `assetlinks.json` 등록 시 설치된 PWA가 브라우저 없이 직접 열림 — 현재 저장소엔 미등록(확인됨) | 무료 | 불필요 |
| (보너스, 한국 특화) 카카오링크 API | 카카오톡 메시지 안에 실제 "앱으로 열기" 버튼을 넣을 수 있는 카카오 공식 **JS SDK**(웹 전용으로 설계된 API라 Stories Sharing과 달리 PWA에서 정상 작동) | 무료 쿼터 + 초과 시 유료 | 카카오 개발자 앱 등록만 |

이 방식은 채널을 가리지 않는다 — 카카오톡·문자·이메일·Instagram DM·X(트위터) 어디로 링크가 퍼지든 동일하게 작동한다. **단, Instagram "게시물/스토리 이미지" 자체에 넣는 방식(캡션 링크 등)은 인스타그램이 캡션 내 링크를 탭 가능하게 안 만들어서 그 채널에서만 안 통한다** — 카카오톡·문자·이메일에선 URL이 정상적으로 하이퍼링크된다.

### Flow C — 조건부 가능, 무거운 전제 필요
"Instagram에 올리면 SPOTCHU에도 자동 반영"은 Pinterest의 "Instagram 계정 연결(claim)" 기능으로 실제 사례가 확인된다(연결 시 인스타 신규 게시물이 자동으로 Pin 생성, 단 동기화까지 2~5일 소요 — 실시간 웹훅이 아니라 폴링 방식으로 추정). SPOTCHU가 이걸 하려면:

- **Instagram Graph API**(`instagram_basic`/`instagram_business_basic`)로 미디어를 읽어야 하는데, **비즈니스/크리에이터 계정만 대상**이다(개인 계정은 API 자체가 안 열림).
- 사용자 본인 계정 하나만 대상이면 **Standard Access**(심사 불필요)로 개발 가능하지만, SPOTCHU가 **여러 사용자의** 계정을 서비스하려는 순간 **Advanced Access**로 격상되고 **Meta App Review가 필수**다(Meta 공식 문서 확인).
- App Review는: 앱 아이콘·개인정보처리방침 등 기본 설정 → 권한별로 "왜 필요한지" 문서 + **영어 UI로 촬영한 스크린캐스트**(실제 동작 시연) 제출 → 심사관용 테스트 안내 제출 → 심사(제출당 2~4주, 승인 불확실). **즉 심사를 넣으려면 기능이 이미 동작하는 상태여야 한다**(자기 계정으로 Standard Access부터 개발 → 이후 Advanced Access 신청, 순서가 강제됨).
- 승인돼도 **실시간이 아니다** — Pinterest 사례처럼 주기적 폴링으로 수 시간~며칠 지연.
- Graph API는 서버-서버 REST 호출이라 PWA/네이티브 여부와 무관하다 — Flow B를 무너뜨린 "웹 API 접근 불가" 문제가 Flow C에는 적용되지 않는다.

> **(v8 재검증)** 위 Flow C 전제는 Meta 공식 문서로 재확인됐고 **전부 유효하다** — *"Requires an Instagram Business or Creator Account"*(개인 계정 미지원), 내가 소유·관리하지 않는 계정을 서비스하려면 Advanced Access, Advanced Access에는 App Review가 필요. **다만 기존 서술이 빠뜨린 조건이 하나 있다: Advanced Access에는 App Review와 별개로 `Business Verification`(사업자 인증)도 요구된다.** Flow C의 착수 비용은 문서에 적힌 것보다 한 단계 더 높다(§미결정 6의 판단 근거로 반영할 것).

### Flow D — 심사 벽은 사라졌지만, 좌표는 API로 안 나온다 (실측 2026-09-08)

**결론**: Flow D는 **Meta 심사 없이 출시 가능한 유일한 Instagram 유입 흐름**이다(Flow C는 심사·사업자 인증 필수). 그러나 **최초 요청의 "#태그를 바탕으로 위치를 보여준다"는 부분은 API로 구현할 수 없다** — 캡션이 응답에 없기 때문이다(실측). 남는 것은 "**게시물 임베드 + 사용자가 직접 지정한 장소 + 지도 + 내 컬렉션 저장**"이며, 이게 Flow D가 실제로 낼 수 있는 최대치다.

> **원천 불가능한 것(설계 고정 — 논의 종료)**
> 1. **해시태그 자동 추출 불가.** 캡션이 oEmbed 응답에 없고(실측), 렌더된 임베드는 교차 출처 iframe이라 클라이언트에서도 못 읽는다. 서버·클라이언트 어느 쪽으로도 길이 없다.
> 2. **좌표 자동 확정 불가.** 응답에 위치 필드가 없다. 설령 캡션을 얻더라도 해시태그는 지명이 아니다 — `#교토`는 도시, `#기온거리`는 거리, `#여행스타그램`은 장소가 아예 아니라서 스팟 하나를 특정할 정밀도가 원리적으로 안 나온다.
>
> → **최종 핀은 항상 사용자가 찍는다.** 이건 우회 대상이 아니라 전제이고, 마침 SPOTCHU의 좌표 불변식(§rules)과 방향이 같다.

> **채택하지 않은 우회로**: `instagram.com/p/{code}/embed/captioned/`는 캡션을 서버 사이드로 렌더링하므로 긁으면 해시태그를 얻을 수 있다. 그러나 이는 **공개 API가 아닌 페이지 스크래핑**이라 Meta 약관 위반 소지가 있고, **PRD §41-1("외부 지오태그 시딩의 법적 적합성 — 법률 검토 필요")** 미결정 항목에 정면으로 걸린다. **법률 검토 전까지 이 경로는 설계에서 배제한다.** 합법적 대안은 §D-7b(사용자가 캡션을 직접 붙여넣기)다.

#### 정정 이력 — 초안이 틀렸던 5건

초안은 기술 블로그·서드파티 API 요약을 근거로 썼고, 1차 출처 재검증과 실측 호출에서 아래 5건이 틀린 것으로 확인됐다. **Flow D의 핵심 결론(심사 불필요·좌표 자동확정 불가)은 재검증에서 오히려 확증됐지만, 세부 설계를 좌우하는 숫자와 범위가 틀려 있었다.**

| # | 초안 주장(2차 출처) | 1차 출처 실측 | 설계 영향 |
|---|---|---|---|
| 1 | 공유시트 수신은 **Android Chrome 전용** | Chromium 계열 전반 지원(Chrome 89 데스크톱 포함). **Safari·Firefox만 미지원** | 범위 오류. "iOS 불가"라는 결론 자체는 유지되므로 붙여넣기 1급 경로 설계는 그대로 |
| 2 | 응답에서 `author_name`·`thumbnail_url`을 얻는다 | Meta 공식 샘플엔 **`html` 외 해당 필드 없음** | **흐름에서 해당 획득 단계 삭제.** 썸네일·작성자명 전제 금지 |

> 5번은 문서 조사만으로는 끝까지 잡히지 않았다 — Meta 공식 문서의 샘플 응답이 `"html": "<blockquote..."` 로 잘려 있어서, **실제로 호출해보고 나서야** 그 안에 캡션이 없다는 게 드러났다. **1차 출처(문서)보다 더 상위 근거는 실측 호출**이라는 것이 이번 패스의 결론이다.

> **교훈(문서 규칙으로 승격)**: 이 문서는 Flow B를 v6에서 폐기하며 "실측 없이 쓰지 않는다"를 배웠는데, Flow D 초안에서 같은 실수가 **출처 등급 문제**로 재발했다. 앞으로 이 문서의 기술 전제는 **1차 출처(플랫폼 공식 문서·표준 기관·공식 가격표)만** 근거로 쓴다. 2차 출처는 1차 출처를 *찾기 위한 단서*로만 쓰고, 근거로 인용하지 않는다.

### Flow D — 공유 페이로드: 유일하게 남은 결정적 미지수

oEmbed(URL로 조회)에 캡션이 없다는 건 실측으로 끝났다. 그러나 **공유 시트는 완전히 다른 통로**다 — 인스타그램 앱이 OS 공유 인텐트에 직접 데이터를 담아 보내는 경로이며, oEmbed와 아무 관계가 없다. **여기에 캡션이 실려 오는지는 아직 모른다.**

이것이 "#해시태그를 분석해 위치를 보여준다"는 원래 요청의 성립 여부를 혼자서 결정한다.

```
인스타에서 [공유] → SPOTCHU 선택
        ↓
   페이로드에 뭐가 들었나?        ← 미확인. 문서 조사로는 확인 불가
        ↓
 ┌──────────────┴──────────────┐
캡션·해시태그 포함              URL 하나만
        ↓                          ↓
원래 요청대로 분석 성립      분석 대상 자체가 없음
                            → D-7a/D-7b로 확정
```

**예상은 "URL만 온다"이지만 근거가 없다**(인스타의 "링크 복사"가 URL만 주는 것과 같은 통로일 것이라는 추론일 뿐). 이 문서에서 추론으로 쓴 주장은 이미 5건이 틀렸다. **확인 없이 설계를 확정하지 않는다.**

#### 확인 방법 — 스파이크 (선행 필수)

`app/manifest.ts`에 `share_target`을 등록하고, 받은 쿼리 파라미터를 그대로 렌더링하는 디버그 페이지 하나를 만든다.

```ts
share_target: {
  action: "/debug/share", method: "GET",
  params: { title: "title", text: "text", url: "url" },
}
```

안드로이드 폰에서 인스타 게시물을 SPOTCHU로 공유해 화면에 캡션이 찍히는지 확인한다. **비용 0, 소요 1시간, Flow D 전체와 플랫폼 전략의 성패가 여기서 갈린다.**

- 주의 1: Android 공유는 `url` 필드를 채우지 않는다 — **URL이 `text`로 들어온다**(Android 공유 시스템에 URL 필드 개념이 없음). 세 필드를 모두 찍어야 한다.
- 주의 2: ~~`share_target`이 Next의 `MetadataRoute.Manifest` 타입에 없을 수 있다~~ → **확인 결과 Next 15 타입에 이미 포함돼 있다**(`next/dist/lib/metadata/types/manifest-types.d.ts`). 캐스팅도 정적 `manifest.json` 분리도 불필요.

**구현 상태(2026-09-08): 스파이크 구현 완료.** [`app/manifest.ts`](../../../app/manifest.ts)에 `share_target` 등록 + [`app/debug/share/page.tsx`](../../../app/debug/share/page.tsx) 디버그 화면. 받은 파라미터를 가공 없이 전부 표시하고 해시태그 유무로 판정을 내린다. 로컬에서 두 케이스(URL만 / 캡션 포함)로 동작 확인했고 `/manifest.webmanifest`에 `share_target`이 정상 노출되는 것도 확인했다. **남은 것은 실제 안드로이드 기기에서 인스타 게시물을 공유해 결과를 보는 것뿐이다.** 확인이 끝나면 이 두 파일을 정리한다.

#### 안드로이드 결과로 네이티브 결과까지 알 수 있다

안드로이드에서는 PWA 공유 대상도 같은 인텐트 시스템을 탄다. **인스타그램은 수신자가 네이티브인지 PWA인지 모르고 알 필요도 없다** — 그냥 인텐트에 데이터를 넣을 뿐이다. 따라서 **안드로이드 PWA에서 URL만 오면 안드로이드 네이티브로도 URL만 온다.** (iOS는 인스타가 다른 항목을 제공할 이론적 가능성이 있으나 확인하려면 iOS 네이티브 빌드가 필요하다.)

#### 플랫폼 선택 — iOS 공유 수신이 필요해질 때만 의미 있음

iOS Safari는 PWA를 공유 대상으로 등록하는 것 자체를 지원하지 않는다(§기술 전제). iOS에서도 "공유 → SPOTCHU"를 쓰려면 네이티브 셸이 필요하고, 선택지는 셋이다.

| 방식 | iOS 공유 수신 | 기존 프론트 | 서버 | 추가 비용 |
|---|---|---|---|---|
| **PWA(현재)** | ❌ | 그대로 | 그대로 | 0 |
| **Capacitor 래핑** | ✅ | **Next.js 그대로 재사용** | **그대로** | 앱스토어 심사·배포·서명 관리 |
| **Flutter** | ✅ (`receive_sharing_intent`) | **전면 재작성** | **REST API 신규 구축 필요(아래)** | 매우 큼 |
| 네이티브 2벌 | ✅ | 전면 재작성 ×2 | 동상 | 가장 큼 |

> **Flutter는 공유 수신 자체는 문제없다.** `receive_sharing_intent`(v1.9.0)가 Android intent-filter와 iOS Share Extension을 함께 감싼다. Android는 `AndroidManifest.xml`에 `SEND`/`SEND_MULTIPLE` intent-filter(SDK 21+), iOS는 **Xcode에 Share Extension 타깃 추가 + App Groups + `RSIShareViewController` 상속 + SPM 활성화**(iOS 13+)가 필요하다. 포크 패키지도 여럿 있으므로 채택 시점에 유지보수 상태를 재확인할 것.

**Flutter 선택 시 숨은 비용 — 서버까지 다시 짜야 한다.** SPOTCHU는 데이터 변경을 **Next.js 서버 액션**으로 처리한다(`"use server"` 파일 6개: auth·moderation·mutations·notifications·profile·notify). REST 라우트는 5개뿐이고 그중 4개는 인프라(nextauth·keepalive·revalidate·upload)라 **실제 데이터 API는 `spots/bounds` 하나뿐**이다. 서버 액션은 React 전용이라 Flutter에서 호출할 수 없으므로, **저장·순서편집·검수·신고·프로필 등 모든 변경 동작에 REST API를 새로 만들어야 한다.** Capacitor는 웹뷰 안에서 서버 액션이 그대로 돌기 때문에 이 문제가 없다.

**스택 규칙 충돌**: `CLAUDE.md`가 Next.js+TS+Tailwind를 고정하고 "임의 대체 금지"로 못박고 있으며, PRD §26 MVP는 "반응형 웹/PWA", 네이티브 앱은 §28-7 **후속 로드맵** 항목이다. Flutter 전환은 기능 결정이 아니라 **제품 스택 전면 교체**이므로 PRD 개정 사안이다.

> **판단 고정**: 공유 진입점 하나만 놓고 네이티브 전환을 결정하지 않는다. **스파이크에서 URL만 온다는 결과가 나오면 어떤 네이티브 방식도 소득이 없다** — 얻는 것은 "붙여넣기 한 번 덜 하기"뿐이고 그것으로 스택 전환을 정당화할 수 없다. 캡션이 오고 **동시에** 네이티브가 필요한 다른 이유(푸시·백그라운드 위치·앱스토어 유통)가 이미 쌓여 있을 때만 검토 대상이며, 그 경우에도 **같은 결과를 훨씬 싸게 내는 Capacitor를 먼저 본다.**

## Flow A — SPOTCHU 콘텐츠 공유 → 딥링크 복귀

### 설계 원칙 (필수)
- **워터마크는 만들지 않는다.** 어느 채널에 올라가든 이미지 자체는 탭 핸들러가 없는 그냥 픽셀이라, 브랜드 오버레이를 합성해도 "보고 자발적으로 검색"이라는 약한 효과 이상을 못 낸다 — 그 효과가 이미지 합성 파이프라인(서버 처리, 실패 케이스, 디자인 결정)을 만들 만큼의 가치가 없다고 판단해 원본 사진을 그대로 공유한다.
- **복귀 링크는 텍스트 채널에서만 작동한다.** 카카오톡·문자·이메일은 URL을 자동 하이퍼링크하지만 Instagram은 캡션·스토리 텍스트를 하이퍼링크하지 않는다 — 이건 SPOTCHU가 고칠 수 없는 Instagram 쪽 제약이라, Instagram으로 공유된 경우엔 복귀 링크가 없다는 걸 그대로 받아들인다(별도 우회 시도 안 함).
- **Instagram Stories의 "배경 이미지 자동 프리필"은 시도하지 않는다.** 네이티브 앱 전용 기능이라 PWA로는 구현 자체가 불가능하다고 확인됨(§기술 전제) — Web Share API로 열리는 일반 공유 시트가 SPOTCHU가 낼 수 있는 최선이다.

### 엣지 케이스
- **딥링크 대상 스팟 소멸**: 04-spot-detail의 기존 "삭제·병합됨" 처리 재사용(새로 만들지 않음).
- **원본 이미지 로드 실패**: 원본 이미지 없이는 공유 진행 안 함(빈 배경 공유 금지). 사진 없는 스팟 공유(스팟 카드형)는 별도 템플릿.
- **저작권**: 공유 이미지는 "내가 찍은 사진(Post.imageUrl)" 또는 스팟 카드(운영자 관리 정보)만 허용, 작품 원본 스틸 사용 금지(prd §24 계승).
- **위치정보**: 공유 이미지도 EXIF 위치 제거 원칙을 그대로 따른다(prd §23) — 원본 사진이라도 예외 없음(업로드 시점에 이미 제거된 상태를 그대로 재사용).
- **공유 앱 목록에 원하는 채널이 없음**(예: 구형 OS): OS 공유 시트 자체의 한계라 SPOTCHU가 대응할 부분 없음.
- **Web Share API 미지원 브라우저**: Firefox 등에선 `navigator.share`가 아예 없음 — 기능 감지 후 URL 복사 버튼으로 폴백.

## Flow D — 남의 인스타 지역 피드 → 구글맵 → 내 컬렉션

> 사용자 요청 원문: "instagram에서 지역에 관련된 피드가 올라와 #태그와 같이 이것을 바탕으로 바로 SPOTCHU와 연동해서 해당 위치 지역을 구글 맵으로 보여주고 저장하는 flow".
> 확정된 두 가지: **피드를 가져오는 주체 = 사용자**(서버 해시태그 수집 아님), **저장 결과 = 내 컬렉션**(공개 스팟 제보 아님).

### 왜 "서버가 해시태그를 수집"이 아닌가
검토했으나 채택하지 않았다. 서버가 `#도쿄여행` 같은 태그를 긁어 지도에 뿌리는 안은 Meta App Review(Flow C와 동일한 2~4주·승인 불확실) + 남의 콘텐츠 대량 보관(플랫폼 정책상 "필요 기간만" 위반 소지) + **PRD §41-1 "외부 지오태그 시딩의 법적 적합성 — 법률 검토 필요"** 미결정 항목에 정면으로 걸린다. 사용자 트리거 방식은 이 셋을 전부 피한다. 서버 수집을 하려면 §41-1 법률 검토가 먼저 끝나야 한다.

### 진입점
| 경로 | 플랫폼 | 비고 |
|---|---|---|
| Instagram [공유] → 공유시트에서 SPOTCHU 선택 | **Chromium 계열 + PWA 설치 시**(Chrome 89·Chrome Android 76·Edge·Opera 76·Samsung Internet) | `share_target` 매니페스트 신규 등록 필요. **Safari(iOS·macOS)·Firefox 미지원** — 모바일 우선 제품이라 실질적으로 iOS 사용자 전체가 이 경로에서 빠진다(§기술 전제) |
| Instagram [링크 복사] → SPOTCHU에서 붙여넣기 | **전 플랫폼** | **1급 경로.** iOS 사용자에겐 이것이 유일한 길 |
| 제보 탭(PR #120으로 승격된 하단 5번째 탭) 내 진입 카드 | 전 플랫폼 | 붙여넣기 입력의 상설 위치 — 신규 화면 만들지 않고 기존 탭에 얹는다 |

### 인터랙션 흐름
```
지민이 Instagram에서 "#교토 #기온거리 #야사카탑" 게시물을 봄
  → (Android) [공유] → SPOTCHU / (iOS·기타) [링크 복사] → SPOTCHU 제보 탭에서 붙여넣기
  → 입력창은 하나뿐이고 붙여넣은 게 URL인지 텍스트인지 서버가 알아서 가른다 (모드 전환 없음)
  → [URL이면] SPOTCHU 서버가 permalink로 oEmbed 호출 (토큰 없음, 공개 게시물만)
      - HTTP 400(Media Not Found) → 비공개·삭제·오타. error_user_msg 기반 안내 후 흐름 종료
      - 성공 → 응답은 html 하나뿐. 이걸 그대로 임베드해 원본 게시물을 화면에 띄운다
        ※ 캡션·해시태그는 이 시점에 서버가 볼 수 없다 (embed.js가 사용자 브라우저에서 그림 — §기술 전제)
        ※ 지민은 화면의 임베드에서 "#교토 #기온거리"를 눈으로 읽을 수 있다. 서버만 못 읽는다
  → [텍스트도 붙여넣었으면] 그 텍스트에서 장소 후보 토큰 추출
      - 지명형 태그 우선(#기온거리 > #교토 > #여행스타그램은 버림)
      - 이 경로는 지민이 캡션을 복사해 왔을 때만 동작하는 선택적 편의 기능이다 (§D-7b)
  → [장소 지정 — 항상 사람이 한다]
    후보가 있으면 그걸 검색어로 프리필, 없으면 빈 검색창
      → 지민이 임베드를 보면서 장소명을 입력·수정
      → Google Places Text Search → 구글맵에 후보 핀 표시(최대 5개)
      → 지민이 핀 선택 · 필요하면 드래그로 위치 조정
  → [저장]
      - 확정 좌표가 기존 SPOTCHU 스팟 반경 내(§미결정 D-2)와 매칭 → 그 Spot을 컬렉션에 저장
        = 기존 원탭 저장 그대로. 신규 데이터 모델 0. 이 경로가 MVP의 전부여도 된다
      - 매칭 없음 → SPOTCHU에 아직 없는 곳 → §미결정 D-1 (개인 장소 vs 제보 전환)
```

### 화면 상태
| 상태 | 조건 | 표시 |
|---|---|---|
| 입력 대기 | 진입 직후 | 붙여넣기 입력창 1개(URL·텍스트 겸용) + 사용법 한 줄 |
| 조회 중 | oEmbed 호출 중 | 로딩(외부 API라 실패 가능성 명시) |
| 비공개·삭제된 게시물 | oEmbed HTTP 400 | `error_user_msg` 기반 안내("공개 게시물만 가져올 수 있어요") + 입력으로 복귀 |
| 임베드 표시됨 · 장소 미지정 | oEmbed 성공 | **기본 상태.** 임베드 + 빈 장소 검색창. 지민이 임베드의 해시태그를 보고 직접 입력 |

| 장소 후보 있음 | Places 결과 ≥ 1 | 구글맵 + 후보 핀 + 후보 목록(임베드 병렬 표시) |
| 장소 후보 없음 | Places 0건 | 지도 + 검색창만, 검색어 수정 유도 |
| 임베드 로드 실패 | embed.js 차단·오프라인 | 임베드 없이도 장소 지정·저장은 계속 가능(임베드는 보조 수단) |
| 위치 확정됨 | 핀 선택·조정 완료 | [내 컬렉션에 저장] 활성화 |
| 기존 스팟과 매칭 | 반경 내 스팟 존재 | "이미 SPOTCHU에 있는 스팟이에요" + 스팟 카드 → 기존 저장 흐름 |
| 매칭 없음 | 반경 내 스팟 없음 | §미결정 D-1 확정 후 작성 |
| 비로그인 | GUEST | 저장 시도 시 소프트 게이트(01 기존 방식 재사용) |
| 레이트리밋 | 무토큰 oEmbed 한도 초과 | "잠시 후 다시" 안내 — 토큰 방식 전환은 §미결정 D-4 |

### 엣지 케이스
- **해시태그가 장소가 아님**(`#여행스타그램`·`#일상`): D-7b 경로에서 지명형 필터에 탈락 → 프리필이 비는 것뿐, 사용자가 직접 입력하는 기본 경로로 자연히 흡수. 에러 아님.
- **검색어가 너무 넓음**(`#일본여행`·"교토"): 국가·도시급 좌표만 나옴 → 저장을 막지는 않되 사용자가 지도에서 좁히도록 유도(정밀도 경고 문구는 §미결정 D-3).
- **여러 장소가 섞인 캡션**(하루 코스 정리 글): D-7b에서 후보 여러 개 제시, **한 번에 하나만 저장**(다중 저장은 스코프 밖).
- **캡션을 볼 수 없는 상황**(임베드 차단·오프라인·embed.js 실패): 서버도 캡션을 모르므로 **아무 힌트가 없다** → 사용자가 기억으로 검색해야 함. 임베드가 이 흐름의 유일한 캡션 표시 수단이라는 점을 UI가 전제해야 한다.
- **게시물이 나중에 비공개/삭제됨**: 저장된 건 좌표·permalink뿐이라 컬렉션 항목은 살아남는다. 임베드만 깨짐 → 임베드 실패 시 좌표·이름만 표시하는 폴백 필요.
- **원본 이미지**: **SPOTCHU에 복제·재호스팅하지 않는다**(PRD §24 + 플랫폼 정책 §기술 전제). 화면에는 Meta가 제공하는 oEmbed 임베드로만 표시.
- **좌표 불변식 충돌**: Places가 주는 좌표는 **장소(피사체)의 위치**이지 SPOTCHU가 정의한 **촬영자가 서는 위치**가 아니다(CLAUDE.md §5·glossary). 이 좌표를 검증된 스팟 좌표로 승격하면 안 됨 → §미결정 D-1의 핵심 쟁점.
- **개인정보**: 애초에 API가 작성자 정보를 주지 않는다(`author_name` 부재 — 실측). 저장 목적이 "내 여행 계획"이므로 작성자 프로필을 다른 경로로 수집하지도 않는다.
- **Instagram 외 링크**(유튜브·블로그·틱톡): 이번 스코프 밖. URL 패턴 불일치 시 명확히 거절.

## 관련 데이터

### Flow A(핵심)
- 신규 필드 없음 — Post·PostImage 재사용. "공유했는지" 여부조차 저장하지 않는다(설계 원칙 참고).
- 이미지 가공 불필요 — 워터마크 없이 `Post.imageUrl` 원본을 그대로 공유한다. Cloudinary 오버레이 트랜스폼 개발 불필요.
- 딥링크: 안드로이드는 Digital Asset Links(`assetlinks.json`) 등록 시 설치된 PWA로 직접 연결 가능(신규 구현 필요 — 현재 저장소에 없음, 확인됨). iOS는 PWA에 대응하는 딥링크 메커니즘 자체가 없음(구조적 한계) — 별도 개발로 해결 불가능하니 시도하지 않는다.
- Deferred Deep Link(Branch/AppsFlyer 등)는 불필요 — 스토어 설치 단계가 없는 PWA라 "설치 후 최초 실행 시 라우팅"이라는 문제 자체가 존재하지 않는다(URL이 항상 즉시 정상 웹페이지로 열림).

### Flow C(Flow A보다 스키마 변경이 큼)
- `User`에 신규 필드: Instagram 연결 여부, 암호화된 접근 토큰, 토큰 만료 시각, 연결 시각.
- 신규 엔티티(또는 테이블) 필요: "가져온 사진 대기함" — 정식 `Post`가 아닌 별도 스테이징 저장소(원본 Instagram media ID, 이미지 URL, 캡션, 가져온 시각, 상태[대기/스팟지정완료/폐기]). 정식 `Post`와 구분해야 하는 이유: 09의 "스팟 비연결 게시물 존재 금지" 불변식을 스테이징 단계에서는 위반할 수밖에 없음(스팟을 모르는 상태로 일단 들어오므로).
- 동기화 배치 작업(주기적 폴링) 인프라 필요 — 기존 프로젝트에 없는 새로운 종류의 서버 작업(cron/큐).

### Flow D(매칭 경로는 스키마 변경 0, 비매칭 경로만 큼)
- **매칭 경로(권장 MVP)**: **신규 스키마 0.** 기존 `Spot` + `Collection`/`CollectionItem` 원탭 저장을 그대로 탄다. 06의 불변식 전부 유지.
- **비매칭 경로**: 신규 저장소 필요 — 06 불변식("컬렉션 항목 = `Spot`")과 좌표 불변식("스팟 좌표 = 촬영자 위치")을 **동시에** 건드리므로 §미결정 D-1 결정 전에는 스키마를 확정하지 않는다.
- **영구 저장 허용 범위**: Instagram permalink URL · 사용자가 확정한 좌표 · 사용자가 붙인 이름/메모. **캡션 원문·이미지·작성자 정보는 영구 저장 금지** — 화면 표시는 요청 시점에 oEmbed `html`을 받아 임베드로 처리한다(애초에 이 필드들을 받지 않으므로 저장할 것도 없다).
- **신규 준수 의무 1건**: Meta Platform Terms §3.d.i.2는 *"provide an easily accessible and clearly marked method for users to request modification or deletion of their Platform Data"*를 요구한다. permalink URL만 저장하는 최소 설계에서도 **저장 항목 삭제 수단이 명확히 노출돼야** 한다(컬렉션 항목 삭제 UI가 이미 있으므로 신규 개발이 아니라 문구·노출 확인 사안).
- **신규 외부 의존 2개**: Instagram oEmbed(무토큰·무료) · Google 지오코딩 계열 API 1개(아래).
- **비용(Google 공식 가격표 기준)** — §D-5 결정 입력값:

  | API | 무료/월 | 초과 시(첫 구간) | 비고 |
  |---|---|---|---|
  | Instagram oEmbed | 무제한(무료) | — | 토큰 불필요. 단 무토큰 레이트리밋 미공개(§D-4) |
  | **Autocomplete — 세션 토큰 사용** | **무제한** | **무료** | `Autocomplete Session Usage` SKU. **반드시 이 방식으로** |
  | Autocomplete — 세션 토큰 없이 | 10,000콜 | $2.83/1,000 | 타이핑 한 글자마다 과금. **이렇게 짜면 안 됨** |
  | Places **Text Search (Essentials)** | 10,000콜 | **$2.27**/1,000 | 최종 확정 1회. POI까지 정확하고 **가장 저렴** |
  | Places Text Search (Pro) | 5,000콜 | $25.60/1,000 | Pro 등급 필드를 요청할 때만 이 SKU로 과금 |
  | Geocoding API | 10,000콜 | $4.00/1,000 | 주소·지명 전용, POI 정확도 낮음. Pro/Enterprise 등급 없음 |

  → **초안의 "Geocoding이 6배 저렴" 판단은 오류**였다. Essentials 필드만 요청하면 **Text Search가 Geocoding보다 싸면서 더 정확**하다. **PRD §41-4(지도 비용 상한)에 새 SKU가 추가되는 건이라 반드시 반영 필요.**

- **비용 결론 — 저장 1건당 과금 호출 ≈ 1회.** 자동완성을 세션 토큰으로 묶으면 타이핑 중 호출이 무료이고 최종 확정 1회만 과금된다. 월 10,000건 저장까지 **$0**, 5만건 약 **$91**, 10만건 약 **$204**. MVP 규모(서울·도쿄, 출시 전)에서는 무료 구간을 벗어나지 않는다.
- **비용을 10~20배로 만드는 함정 2개(구현 규칙으로 고정)**:
  1. **자동완성에 세션 토큰을 반드시 쓴다.** 세션 토큰 없이 as-you-type을 구현하면 키 입력마다 과금된다.
  2. **요청 필드를 코드에서 화이트리스트로 고정한다.** Pro 등급 필드(평점·리뷰 등)를 하나라도 요청하면 단가가 $2.27 → $25.60으로 **11배** 뛴다.
- **⚠️ Places는 서버 전용 API 키를 새로 발급한다(보안).** 현재 저장소에는 `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`만 있고 이 키는 **브라우저에 그대로 노출된다**(Maps JS API 특성상 정상). 이 키에 Places를 활성화하면 **노출된 키로 제3자가 우리 과금을 태울 수 있다** — HTTP referrer 제한은 우회가 쉽다. 장소 검색은 서버에서 호출하므로 **`NEXT_PUBLIC_` 없는 서버 전용 키를 별도 발급하고 IP 제한을 건다.**
- **`embed.js`는 인스타그램 제3자 스크립트다.** 임베드 렌더링에 `//www.instagram.com/embed.js` 로드가 필요하다. 현재 저장소에는 **CSP 설정이 전혀 없어**(`next.config.mjs`·`vercel.json` 확인) 당장 차단되지 않으나 — (a) 이후 CSP 도입 시 `script-src`/`frame-src`에 instagram.com 허용 필요, (b) 인스타가 쿠키·트래킹을 심으므로 **개인정보처리방침에 제3자 스크립트 고지가 필요할 수 있다**(PRD §23 연동, 법무 확인 권장), (c) 광고·트래커 차단기에 막히면 캡션이 안 보여 흐름이 크게 나빠진다(§화면 상태 "임베드 로드 실패").
- Flow C와 달리 **토큰 저장·갱신·폴링 인프라가 전부 불필요**하다(요청 시점 호출뿐).
